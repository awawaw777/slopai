# SlopAI — проверенная сборка Flask + SQLite

Учебный магазин компьютеров: каталог, поиск, фильтры, конфигуратор, корзина,
регистрация, вход, оформление заявки и удаление своих заказов. Внешний вид
и основные сценарии сохранены. Платежей и реальных интеграций нет.

Python 3.10+. Проверено на Python 3.12 / Linux. Исходное Windows-окружение
`.venv` исключено: зависимости устанавливаются заново из PyPI, с проверкой
SHA-256. Windows-команды приведены ниже, но запуск на Windows не проверялся.

## Быстрый запуск на своём компьютере

Распакуйте ZIP и откройте терминал в папке с `app.py`.

Windows PowerShell:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install --only-binary=:all: -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Linux / macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --only-binary=:all: -r requirements.txt
.venv/bin/python app.py
```

Откройте http://127.0.0.1:5000. При первом запуске создаются пустая база
и новый случайный ключ в `instance/`. Готовых аккаунтов и стандартных паролей нет.
Зарегистрируйте тестовый аккаунт; новый пароль — 12–128 символов.
Используйте вымышленные адреса и телефоны.

Режим по умолчанию `APP_ENV=local`: только loopback-интерфейс, локальные Host
и локальные клиенты. Он работает через HTTP без Secure-cookie. Не используйте
его для публикации в сеть. `PORT` меняет порт; `HOST` по умолчанию `127.0.0.1`.
Если в окружении остались настройки другого проекта, проверьте их перед запуском.

## Размещение через HTTPS

| Переменная | Значение |
| --- | --- |
| `APP_ENV` | `production` |
| `SECRET_KEY` | Новый случайный секрет, не менее 32 символов |
| `TRUSTED_HOSTS` | Ваш домен, например `shop.example`; список через запятую |
| `COOKIE_SECURE` | Необязательна: Secure включён автоматически; `0` запрещён |

Сгенерировать секрет: `python -c "import secrets; print(secrets.token_hex(32))"`.
Сохраните его в окружении сервиса или менеджере секретов. Приложение не загружает
`.env` автоматически. Не добавляйте значение в исходники.

Production не использует `instance/secret.key`, требует HTTPS и отключённого
DEBUG. Cookie называется `__Host-session`, имеет Secure, HttpOnly, SameSite=Lax,
Path=/ и не имеет Domain. HTTP-запросы отклоняются. HTTPS-прокси должен
перенаправлять HTTP на HTTPS до отправки в приложение.

Waitress сам не завершает TLS. Пример команды **только для одного доверенного
HTTPS-прокси на том же сервере**, после установки переменных окружения:

```bash
.venv/bin/waitress-serve --listen=127.0.0.1:5000 --trusted-proxy=127.0.0.1 --trusted-proxy-count=1 --trusted-proxy-headers="x-forwarded-for x-forwarded-proto" --max-request-body-size=32768 --max-request-header-size=16384 --call app:create_app
```

Прокси должен передавать проверенный Host и **перезаписывать** X-Forwarded-For
и X-Forwarded-Proto значениями соединения. Адаптируйте пример при другом числе
прокси или другом IP. Не доверяйте `*`. Приложение само не доверяет X-Forwarded-*;
это проверяет Waitress. Доступ к backend-порту ограничьте прокси. TLS, внешние
лимиты нагрузки, обновления ОС и резервные копии настраиваются при развёртывании.

На POSIX каталог `instance` получает права 0700, ключ и база — 0600.
На Windows ограничьте ACL каталога учётной записью сервиса; POSIX-права
не заменяют Windows ACL. SQLite храните на постоянном локальном диске.

## Если предыдущая версия уже использовалась

Исходный архив содержал ключ cookie и базу с аккаунтами. Считайте эти данные
раскрытыми. Новый архив не содержит `instance/` и не переносит старый секрет.

1. Остановите старый сервер и сделайте защищённую резервную копию базы.
2. Если нужны прежние аккаунты/заказы, перенесите **только** `slopai.sqlite3`
   в новый `instance/`. Не копируйте `secret.key`, `.venv` или `.idea`.
3. Для local новый ключ создастся автоматически; в production установите
   новый `SECRET_KEY` в окружении.
4. Выполните в новом окружении `python -m flask --app app:create_app revoke-sessions`.
   Команда отзывает все входы, сохраняя аккаунты и заказы.
5. Если аккаунты были настоящими, смените раскрытые пароли, особенно при
   повторном использовании в других сервисах. Здесь нет формы сброса пароля;
   безопаснее создать новые тестовые аккаунты в пустой базе.

Вход в старые аккаунты с паролем короче 12 символов сохранён для совместимости;
минимум 12 действует для новых регистраций. Старые cookie после смены ключа
отклоняются. `SECRET_KEY_FALLBACKS` не используется.

## Проверки и сборка

Из корня проекта, используя Python установленного окружения:

```bash
python -m unittest discover -s tests -v
python -m pip check
python build_release.py
```

35 тестов проверяют магазин, SQL-инъекции, XSS, CSRF, чужие заказы, подмену цены,
повторы отправки, отзыв и истечение сеансов, смену ключа, Origin, HTTPS, права
файлов, конкурентное создание ключа и исключение секретов из архива.

Сборщик создаёт `dist/slopai-secure.zip` и `.sha256` по списку разрешённых файлов.
Runtime-данные, виртуальное окружение и настройки IDE не включаются. При одинаковых
исходниках ZIP воспроизводится побайтно. Не добавляйте секреты непосредственно
в разрешённые исходники или отчёты.

Для повторного аудита создайте отдельное окружение инструментов:

```bash
python -m venv .audit-venv
.audit-venv/bin/python -m pip install -r requirements-audit.txt
.audit-venv/bin/bandit app.py catalog.py security.py build_release.py -f json -o audit/bandit-after.json
.audit-venv/bin/pip-audit -r requirements.txt --cache-dir .audit-cache -f json -o audit/dependencies-after.json
```

На Windows используйте `.audit-venv\Scripts\...` вместо `.audit-venv/bin/...`.
Регулярно обновляйте версии вместе с хешами и повторяйте проверки. Отчёты в
`audit/` относятся к приложенной сборке, а не к последующим изменениям.

## Защитные механизмы

- Параметризованный SQL, проверка владельца при чтении и удалении заказа.
- Серверный расчёт цены и совместимости, ограничение корзины.
- Scrypt для паролей, отзываемые сеансы с хранением хешей токенов на сервере.
- CSRF, проверка Origin и Sec-Fetch-Site, ограниченные redirect.
- Экранирование Jinja, вывод JS через textContent, CSP.
- Тело запроса до 32 КиБ, ограничение полей, IP/аккаунт-лимиты в SQLite.
- Ошибки без traceback для клиента, no-store, nosniff, запрет iframe, HSTS на HTTPS.

Удаление заказа требует POST, CSRF, входа и подтверждения. Состав и контакты
удаляются, технический маркер повторной отправки сохраняется. Номера удалённых
заказов не используются повторно. Резервными копиями управляет оператор.

Подробности находок и ограничений — в `SECURITY_REPORT.md`.
