# Отчёт о проверке SlopAI

Дата: 2026-10-01. Проверка исходников, настроек, зависимостей и локальных
сценариев Flask. Реальный сервер, ОС и конфигурация HTTPS-прокси не предоставлялись.

## Исходный материал

Архив: `slopai-flask.zip_pass_123.7z_pass_123.zip`.

SHA-256 входного файла:
`69a5c22e138c3c93b9944c9012020e6d4a7007275ba7f0d51b45d5041d197723`.

Оба слоя открыты паролем `123`. Перед распаковкой проверены размер,
пути и отсутствие символических ссылок. Исходные программы из `.venv`
не запускались. Для проверок зависимости заново установлены из PyPI.

## Подтверждённые находки

| Находка | Оценка и последствия | Исправление |
| --- | --- | --- |
| В поставке присутствовал `instance/secret.key` | Высокая: получатель знает ключ подписи Flask-cookie и может формировать подписанные клиентские данные. Серверные auth_sessions ограничивают непосредственный захват аккаунта: одной подмены user_id недостаточно. | Ключ исключён; новый создаётся для каждой локальной установки. Production требует отдельный SECRET_KEY и не читает старый файл. |
| В поставке присутствовала рабочая SQLite-база | Высокая для конфиденциальности: 2 аккаунта, 1 активная запись сеанса, 4 записи лимитера и 1 технический маркер заказа; заказов 0. Персональные поля и хеши не публикуются. | База исключена; новая установка пустая. Есть команда отзыва всех сеансов и инструкция по смене ключа. |
| Flask 3.1.2 содержит CVE-2026-27205 / GHSA-68rp-wp8r-4726 | Условный риск кеширования данных сеанса. Исходный Cache-Control: no-store уже снижал применимость. Аудитор вернул две дублирующие записи PYSEC-2026-2151: это одна уникальная CVE. | Flask 3.1.3. Отчёты до/после приложены. |
| HTTP-cookie и сетевой запуск не разделены конфигурацией | Оператор мог открыть сетевой HOST, забыв COOKIE_SECURE. Исходный запуск по умолчанию уже был на loopback. | Local ограничен loopback; production требует HTTPS, Secure-cookie, секрет и отключённый DEBUG. Добавлены __Host-cookie и проверка Origin. |
| Каталог instance и SQLite создавались с системной umask | При типичной POSIX umask 022 возможно чтение БД другими локальными пользователями. Сам ключ уже создавался с 0600. | Каталог 0700, база/ключ 0600 на POSIX; отклоняются ссылки. Для Windows документированы ACL. |
| Часть зависимостей не закреплена; поставлялась чужая .venv | Невоспроизводимая установка и лишние исполняемые файлы. | Runtime-зависимости закреплены по версии и SHA-256. .venv, .idea, кеши и runtime-данные исключены. |

В исходной `.venv` был Werkzeug 3.1.8; в новой сборке 3.1.9.
Отдельный аудит версий из вложенного окружения приложен. Его файлы
не использовались как доверенные зависимости.

## Дополнительные исправления

- Тестовая конфигурация применяется до чтения/создания настоящего ключа.
- Первый локальный ключ публикуется атомарно: одновременные старты получают
  одно полное значение, а не временно пустой файл.
- Новые пароли: минимум 12 символов; старый вход совместим с прежними хешами.
- Управляющие символы отклоняются в имени/адресе, телефон ограничен допустимыми символами.
- Индекс времени ускоряет очистку устаревших записей лимитера.
- Сборка по списку разрешённых путей предотвращает повторное включение instance.

Существовавшие защиты от SQL-инъекций, XSS, CSRF, чужих заказов, подмены цены,
повторов заказа и использования cookie после выхода сохранены.

| PNG-ресурс | Контрольные суммы блоков корректны, лишних байтов после IEND нет | `audit/asset-check.json` |

Тесты используют временные базы. Проверяются HTTPS-cookie, отказ HTTP и
поддельному X-Forwarded-Proto, чужой Origin даже при корректном CSRF,
отзыв входов, смена ключа, права POSIX и одновременное создание ключа.
При проверке Waitress исправлен конфликт двух отказов: HTTP с чужим Host
теперь получает 400, без попытки построить HTML-страницу через отсутствующий
маршрутизатор. Сценарий добавлен в регрессионный тест.
Исходный и итоговый Bandit не нашли предупреждений: проблемы поставки
секретов и конфигурации обнаружены ручной проверкой, а не этим сканером.

Изменения отражены в `audit/changes.patch`; секреты и рабочая база в patch
не включены. Результаты относятся к версиям и базам уязвимостей на дату
проверки; нулевые находки не доказывают отсутствие всех уязвимостей.

## Границы проверки

В просмотренных исходниках приложения и JavaScript не обнаружены явные
загрузчики, команды ОС, eval/exec, небезопасная десериализация или отправка
данных на сторонние адреса. Это не антивирусное заключение: антивирусная
и динамическая проверка всех PE/PYD/PYC-файлов исходного Windows-окружения
не выполнялась. Они не включены в новый архив.

Проверки выполнялись на Python 3.12 / Linux. Windows/macOS не запускались;
POSIX-права не гарантируют нужные ACL на Windows. pip-audit на Linux проверяет
активные зависимости этой платформы; условный Windows-пакет Colorama проверен
отдельно (`audit/dependencies-windows-extra.json`).

Не проводились полномасштабный пентест, нагрузочное тестирование, проверка
инфраструктуры и TLS. Для реального магазина нужны мониторинг, управление
секретами, обновления, резервные копии, подтверждение email, восстановление
пароля и политика хранения персональных данных. Общие лимиты IP могут
затронуть пользователей за NAT; production требует корректного доверенного
прокси. SQLite рассчитан на учебную/небольшую нагрузку.

Оценка сторонней нейросети неизвестна. В отчёте не подменяются критерии
проверки и не заявляется гарантированный балл.
